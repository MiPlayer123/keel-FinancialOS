# KEEL Stage 1C Plan (v3) — Plaid Sandbox Read Path (server-only, correctness-first)

**Status:** v3, after two dual-audit rounds (Claude + Codex). Round 2 verdict: v2 was still too big and several ingestion subsystems were under-designed. v3 **splits the stage** and designs each hard subsystem to the exact mechanics the audits demanded.
**Builds on:** Stage 1A (tagged `stage-1a`, deployed). Reuses the deterministic ledger, command/worker procs, verified-webhook ordering, RLS/grant posture, and the pure planner (with one amendment, D-D).
**Controlling specs:** INFRA.md §4/§5/§8/§9/§14/§16 → BC-v2.1 §3/§6 → docs/17 §3 → CLAUDE.md Laws 1,2,4,5,6,9,12.

## 0. Thesis (split narrow) — D-022

> A signed-in user links a Plaid **Sandbox** item; KEEL pulls its **USD** transactions through a correct, crash-safe sync onto the existing ledger; access tokens are envelope-encrypted and **never enter Postgres in plaintext or cross an RPC boundary**; correctness is proven by the *existing* `keel_trial_balance` / `keel_list_transactions` queries against a real Sandbox item.

**Split (resolves round-2 "too big" + INFRA §16 placement):**
- **This stage (1C): server-only Plaid read path.** No new UI, no export.
- **Export → Stage 1D** (INFRA §16 places exports there; the round-2 "Law-6 silently stubbed" objection is resolved by *not doing a partial export now*, and 1C adds nothing that makes data unexportable).
- **Viewer UI → Stage 1E** (INFRA §16). 1C proves end-to-end via API queries, not pixels.
- Already cut in v2 and staying cut: categorization, CSV import, transfers/exclusion, professional access, `periods.reopen`, multi-currency, receipts.

## 1. Design decisions (the hard parts, resolved)

### D-A. `connections` **is** the Plaid Item; retrofit composite tenant FKs; one unambiguous item id (Codex #6, Claude M6)
- No new Item table. Amend `connections`: add `institution_id`, `consent_expires_at`, `last_successful_sync_at`. `external_ref` **remains the sole physical item identifier** (rename in comments to "provider item id"); no alias column (avoids two mutable identities).
- **Routing:** the deployed webhook lookup keys on `(provider, external_ref)` but the uniqueness constraint is `(household_id, provider, external_ref)`. Make Plaid item ids globally unique by **adding a partial unique index `unique (provider, external_ref) where provider='plaid'`** (Plaid item ids are globally unique), so the STRICT webhook lookup can never be ambiguous. Keep the household-scoped unique for simulator.
- **Tenant-integrity retrofit** (migration C2a): add parent uniques `connections(household_id, id)`, `accounts(household_id, id)`, `canonical_transactions(household_id, id)`, `normalized_source_records(household_id, id)`; convert **all** hot-path children to **composite FKs** so a child's `household_id` cannot disagree with its parent's. Under Postgres FK default `MATCH SIMPLE`, a composite FK is simply **not enforced when any referencing column is NULL** (so nullable `connection_id` for manual accounts is fine — the row is skipped, not rejected):
  - `accounts(household_id, connection_id) → connections(household_id, id)`
  - `raw_provider_events(household_id, connection_id) → connections(household_id, id)` (connection_id NOT NULL here; ADD CONSTRAINT scans the table — trivial on a day-old DB)
  - `normalized_source_records(household_id, account_id) → accounts(household_id, id)`
  - **`canonical_transactions(household_id, account_id) → accounts(household_id, id)` and `(household_id, entity_id) → entities(household_id, id)`** (round-2 gap Codex re-flagged: the deployed table has independent household/account FKs)
  - **`transaction_source_links`: add `household_id` and composite-FK both sides** — `(household_id, canonical_transaction_id) → canonical_transactions(household_id, id)` and `(household_id, normalized_source_record_id) → normalized_source_records(household_id, id)` — closing the cross-household link path.
  - new satellites likewise.
  A migration-compatibility subsection proves, per consumer (accounts, raw_provider_events, normalized, canonical, transaction_source_links, sync_checkpoints, worker procs, webhook), that no existing signature/constraint changes semantics.
- Credential owner is modeled independently (BC §3): `connection_credentials.credential_owner_user_id`.
- **Raw evidence is verbatim (Codex major):** `raw_provider_events.body jsonb` cannot preserve exact bytes, key order, or numeric lexemes. Amend the table to add immutable `body_text text` + `body_sha256 text` (the exact response bytes); the existing `body jsonb` becomes a **derived** convenience column. This is the source of truth for D-E lossless numeric parsing and for source-preservation (Law 5). Append-only triggers already protect it.

### D-B. Credential crypto — KEK in Edge secrets, per-token DEK, **plaintext never enters Postgres** (Codex #1, Claude Blocker 1)
Supabase Vault has no DEK-wrap primitive and a DB proc cannot hand plaintext to an Edge HTTP call without returning it over RPC — so **encryption lives in the Edge function, not the database**:
- `KEEL_CREDENTIAL_KEK` (+ `..._KEK_VERSION`) live in Supabase Edge Function Secrets (never in DB, never a proc arg).
- On exchange (Edge, in memory): generate a random 256-bit **DEK** + a fresh random **96-bit IV per encryption** (never reused), AES-256-GCM-encrypt the Plaid `access_token` with the DEK, wrap the DEK with the KEK (AES-GCM). Bind **AAD = `credential_id || household_id || provider || kek_version`** on both encrypt and wrap so ciphertext can't be replayed across rows/tenants. Only `{ciphertext, iv, wrapped_dek, wrap_iv, kek_version}` — **never plaintext** — is passed to `connections.finalize_link`.
- The **worker** (Edge), immediately before a Plaid call, reads the ciphertext row, unwraps the DEK with the KEK, decrypts the token **in Edge memory**, calls Plaid, and drops the plaintext. Postgres only ever holds ciphertext.
- **Rotation** = re-wrap DEKs under a new KEK version (operator Edge routine); tokens are not re-encrypted. Old KEK versions retained until re-wrap completes.
- **Disconnect** crypto-shreds by deleting the wrapped_dek (token unrecoverable) — only after `/item/remove` succeeds (D-F).
- Gates: no plaintext secret — **access token, link token, or public token** (all three classes, Claude NF-3) — ever appears in any RPC arg/result, `RAISE`/exception `DETAIL`/`CONTEXT`, structured log, dead-letter, audit/domain/health row, Storage, or DB column — proven with **unique canaries** swept across all sinks; the C2b/C5 review checklist explicitly forbids any `RAISE`/exception path from including decrypted material; KEK rotation then a successful sync. `connection_credentials` (and the `link_attempts.credential_ciphertext`) get zero `anon`/`authenticated` grants or policies.

### D-C. Durable sync lease + attempts; atomic per-page; mutation abandons, never deletes (Codex #2/#3, Claude M5)
Replace the xact advisory lock (can't span HTTP round-trips) with durable state:
- **Lease** on `connections`: `sync_lease_owner uuid, sync_leased_until timestamptz, sync_desired_generation int, sync_committed_generation int`. A worker CAS-acquires the lease (advisory lock only guards the short acquire txn) and **renews `leased_until` per page** so a multi-invocation pull keeps the lease; an expired lease is reclaimable via CAS (stranded-lease safe). Every `SYNC_UPDATES_AVAILABLE` notification bumps `sync_desired_generation`; on completion, if desired > committed the worker requeues (no lost signal). The lease is the **fencing token** — a stale worker whose lease was reclaimed fails its CAS and cannot commit.
- **`sync_attempts`** (attempt_id, connection_id, base_cursor, next_request_cursor, page_ordinal, generation, state `open|completed|abandoned`, promoted_at). **Bounded pages per invocation** (Free Edge Functions have a ~150s wall-clock limit and INFRA §9 forbids a full backfill in one invocation): pull up to N pages, persist `next_request_cursor` + renew lease, re-enqueue if `has_more`.
- **Raw archival (collision-safe, Codex #2):** each page is an **immutable `raw_provider_events`** row keyed by `provider_event_id = attempt_id || ':' || page_ordinal` — deterministic **within an attempt** (idempotent re-archive on same-attempt retry via `ON CONFLICT DO NOTHING`), and a *new* attempt (new `attempt_id`) writes distinct rows. This sidesteps the unsafe cross-pull `sha256(base_cursor||ordinal)` id, since Plaid does **not** guarantee stable page boundaries across re-pulls. Abandoned attempts' raw rows are **retained as evidence but excluded from reconciliation** by attempt state. The `raw_provider_events` row stores **verbatim `body_text` + `body_sha256`** (see D-E / the raw-verbatim amendment) with parsed `jsonb` as a derivative. The "no double-archive" gate is scoped **within a single attempt**.
- **Mutation restart** (`TRANSACTIONS_SYNC_MUTATION_DURING_PAGINATION`): mark the attempt `abandoned` (evidence retained), start a new attempt from the committed base cursor.
- **Completion + promotion barrier (Codex #2):** on `has_more=false`, mark the attempt `completed`, then run reconciliation+promotion (D-D) of that attempt's full event set, and **CAS-advance `sync_checkpoints.cursor` only after promotion of this attempt is durably complete** (`promoted_at` set). **A new attempt may not begin planning while the connection has any un-promoted completed attempt** — per-connection promotion is ordered; the lease-acquire check refuses to plan ahead of an unfinished promotion. This closes the "later sync plans against canonical state before the prior promotion lands" hole. Cursor advances **only** on a fully-promoted completed attempt; a crash re-pulls from the committed cursor.

### D-D. Pending→posted **set reconciliation**; planner amendment; explicit removals (Codex #4/#3, Claude — planner)
Real Plaid splits supersession across `added`/`removed` (pending id in `removed`, posted in `added`) — the 1A planner (which expected a single `added` with `pendingTransactionId`) would double-count or void the posted row.
- **Plaid invariant (cited, Codex-verified):** when a pending transaction posts, that single `/transactions/sync` update carries the pending id in `removed` **and** the posted transaction in `added` (with `pending_transaction_id` = the pending id). Because a completed attempt drains **all pages to `has_more=false`**, both halves are always in the *same completed attempt's* aggregate set — so single-completed-attempt reconciliation is provably sufficient; no cross-attempt pairing window is needed (Claude NF-2 resolved).
- After a **completed** attempt, reconcile the whole added/modified/removed set **as a batch**, evaluated **against already-promoted canonical state** (via `keel_worker_lookup_state`, so a pending P promoted in a *prior* attempt is visible): pair `removed(P)` with `added(Q, pending_transaction_id=P)` into **one supersession** (continue P's economic key, status→posted) and **suppress the standalone removal**; a `removed` with no matching `added` in the set is a true void; `modified` updates in place.
- Extend `packages/ingest`: add `reconcileSyncBatch(events, priorState) → PromotionAction[]` consuming the full set (the existing per-event `planEvent` becomes a helper). Unit-test both page orders, a P-promoted-in-earlier-attempt-then-posts case, crashes, replay.
- **Amend `keel_worker_apply_promotion`**: it currently *creates* `normalized_source_records` itself — change it to **consume a pre-created normalized event id** produced during the fan-out (raw→normalized happens once, in the sync path; planner/promotion operate on normalized ids). The proc **derives/validates action data from the referenced normalized row**, not from a duplicated caller payload. The normalized schema gains explicit `kind (added|modified|removed)`; **removal rows are representable as tombstones** — `account_id`/`amount_minor`/`currency`/`effective_date`/`description` become **nullable when `kind='removed'`** (a removal carries only the superseded `provider_transaction_id`), enforced by a CHECK. `keel_worker_lookup_state` continues to read status from `canonical_transactions.status` (not the normalized `kind`), so a tombstone doesn't corrupt the view.

### D-E. Decimal→minor, lossless, exact sign (Codex #5, Claude M7)
- **Lossless capture**: `response.json()` floats the number, so keep the **verbatim response text** (`raw_provider_events.body_text`, the same bytes archived in D-C) and parse it with a **numeric-lexeme-preserving JSON parser** (e.g. `json-bigint`/a reviver that keeps `amount` as its source string) — the decimal never passes through JS `Number`.
- **New `decimalToMinor(lexeme, currency)`** (distinct from `parseMinorUnits`, which is integer-only): accept `-?\d+(\.\d{1,2})?` for USD (scale 2); **reject** (don't round) >2 fractional digits, non-USD `iso_currency_code`, or int64-overflow. Pure string→bigint (pad/scale digits, strip the dot), no float; the resulting integer string then feeds `parseMinorUnits`.
- **Sign**: Plaid `amount` is **positive = money leaving the account** (Codex-verified; not account-type-dependent). KEEL stores holder-perspective signed minor units, debit-positive assets; the adapter negates Plaid's sign to the holder's perspective; a property test pins credit + depository cases.
- **Per-transaction** currency check (account-level USD activation is necessary but not sufficient); non-USD events are **skipped at normalize-time with a recorded reason** (not dead-lettered).

### D-F. Durable link/disconnect saga (Codex #7)
- `link_attempts` (id, household, status `started|exchanged|finalized|abandoned`, created_at, expires_at, **credential_ciphertext**). `connections.begin_link` records an attempt (no Item yet); the Edge function calls Plaid `/link/token/create` then, after Link, `/item/public_token/exchange` (public token never logged) **then `/accounts/get`** (the account bootstrap Codex flagged — exchange returns only token+item_id, and the worker requires an existing account mapping). **Immediately after exchange, the encrypted token ciphertext is persisted onto the `link_attempt` row** (so an orphan reaper has a credential to call `/item/remove` with — Codex reaper fix); `connections.finalize_link` then **atomically adopts** that ciphertext + creates the `connections` row + accounts from `/accounts/get` (USD gate) + audits + enqueues initial sync. A reaper calls `/item/remove` (using the persisted ciphertext) for orphaned `exchanged` attempts past expiry; if ciphertext persistence itself failed, a best-effort `/item/remove` runs while plaintext is still in Edge memory.
- `removal_attempts` + transitional status `disconnecting`: invalidate sync generations first → retry `/item/remove` → on success crypto-shred DEK → mark `disconnected`. Shred never precedes a confirmed remove.

### D-G. Metering + breakers (Codex #10 / INFRA §14)
`usage_events` row per Plaid/JWK/link/exchange/remove/institution call (kind, latency, error, request_id — **no secrets**). Breakers: per-item sync-rate, per-item concurrent-attempt (via lease), and a global daily Plaid-call budget. (Storage/export breakers move to 1D with export.)

## 2. Account lineage (Codex #9, Claude — lineage)
Prefer the provider `account_id` for same-item mapping, but Plaid documents `account_id` can change even within an item; so whenever an account id disappears and another appears, run **scored candidate matching** (institution, subtype, mask, name, currency, prior balance, overlapping transactions) and **require user confirmation** when identity isn't uniquely proven. Never auto-create a second economic account or auto-merge on a tuple. Record reason/evidence/effective-dates/actor/old-new ids in `account_lineage`. Known 1D gap (documented): cross-item transaction de-dup (economic key embeds item id).

## 3. Item lifecycle
`linking → active`; `active →(ITEM_LOGIN_REQUIRED/ITEM_ERROR) reauth_required` (+health event; **guard: no raw/canonical writes while reauth_required**, checked at job-claim and immediately before each write); `reauth_required →(update-mode relink + finalize) active`; `active|reauth_required →(user) disconnecting → disconnected` (D-F). `PENDING_EXPIRATION`/`PENDING_DISCONNECT`/`LOGIN_REPAIRED` set/clear `reauth_required`.
**Interactivity scope (Codex new blocker):** update-mode relink requires an interactive Plaid Link session, which a server-only stage cannot drive. **1C tests the server-side state transitions** (`ITEM_LOGIN_REQUIRED → reauth_required → active` driven by a scripted finalize, and the reauth write-guard) with Sandbox `/sandbox/item/reset_login`; the **live interactive update-mode gate defers to 1E** (the UI stage). Until 1E, `reauth_required` is terminal-until-manual-relink — stated, not silent.

## 4. Webhook hardening (unchanged from v2 §4, retained)
Verify-then-store (D-013, now elevated to an explicit amendment of doc 17 §3 — D-021); bounded body size; `environment='sandbox'`; `alg=ES256` + `kid` + recent non-future `iat` + exact body hash constant-time compare; JWK cache by `kid` with TTL + negative-cache/rate-limit unknown kids; distinguish invalid-signature (401, quarantine) from JWK-fetch outage (5xx, retryable); dedupe delivery by signed-JWT-fingerprint + body-hash (not `request_id`); webhook is an idempotent "sync this item" trigger.

## 6. Acceptance gates
Scripted + live-Sandbox: pending-removed+posted-added across pages (both orders, crash, replay) → one economic history; mutation-restart mid-pagination → clean restart from committed cursor, no double-archive; concurrent notifications → lease serializes, no lost generation; ITEM_LOGIN_REQUIRED → reauth → update-mode → catch-up; initial empty sync; JWK rotation/outage (retryable vs invalid); stale job rejected by generation CAS. Plus: tenant isolation on every new table via other-household ids through commands **and** service-role worker calls; **Law 12** token-canary sweep across all sinks + KEK rotation then sync-works; decimal→minor property test (rounding-reject, sign, bounds); per-transaction USD rejection recorded (not dead-lettered — normalize-time skip); red-team re-run on Plaid fields (`name`, `merchant_name`, `original_description`, `personal_finance_category`). Reuse `keel_trial_balance`/`keel_list_transactions` to assert the ledger matches the Sandbox item.

## 7. Human checkpoints (⚑)
Rotate Plaid Sandbox secret + provision client id before any call; **KEK generation/provisioning** + **crypto security review** (C2b); Plaid Dashboard webhook/redirect config for the cloud endpoint; sanitized-fixture approval (C0); first live dynamic-Sandbox link/sync; reset-login/update-mode run. Production linking remains a separate later ⚑ (doc 17 §3). A single happy-path link is not a sufficient live gate.

## 9. Round-3 audit closure
