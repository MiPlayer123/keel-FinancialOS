## Business rules implied
- A single expense can be pivoted/grouped by exactly one of five dimensions at a time — Merchant, Employee, Budget, Status, or Trip — implying these are the canonical facets Brex considers first-class for expense organization (`community-01-expenses-table-grouped.jpg`).
- Groups display both a "loaded so far / total" count and a running dollar subtotal simultaneously (e.g., "2 of 322 ($11,293.98)"), implying subtotals are computed over the full group, not just the visible/loaded rows (`community-01-expenses-table-grouped.jpg`).
- Accounting export is modeled as a three-stage pipeline — Prepare → Review → Exported — with each stage carrying its own count, i.e., a transaction cannot go straight from raw import to "Exported" without passing through discrete, visible stages (`community-02-accounting-queue.jpg`).
- Bulk export actions require an explicit selection count and produce a distinct "prepared as accruals" sub-status before actual export, implying an intermediate accrual-preparation step separate from the export action itself (`community-02-accounting-queue.jpg`).
- Every transaction row requires a Debit GL account mapping (shown unset via "Select" placeholder) before it can be considered export-ready, implying GL-account assignment is a mandatory per-row field gating the Prepare→Review/Export pipeline (`community-02-accounting-queue.jpg`).
- Bill/payment approval routing is threshold-based by default (payments ≥$50K require another admin's approval) but can be fully customized or disabled outright, implying three mutually exclusive top-level approval postures exist (`community-03-payment-approval-settings.jpg`).
- Receipt validation is field-level and can partially fail (amount mismatch) while other fields (date, merchant) pass, and the receipt is still labeled "Verified" overall — implying "Verified" denotes an automated-check-was-run status, not unanimous-pass (`community-04-receipt-validation.jpg`).
- Receipts can exist unattached to any transaction ("Unmatched receipts"), and the matching action is manual per-receipt ("Attach"), implying receipt capture and transaction posting are decoupled processes reconciled by user action (`community-05-unmatched-receipts.png`).
- Custom accounting rules can source their condition from an external ERP field (NetSuite Department) with multi-value list matching, implying the rule engine is designed to key off third-party/synced dimensions, not just Brex-native transaction fields (`community-06-custom-accounting-rule.png`).
- Policy rules can hard-block a transaction outright based on merchant category code (MCC) membership in a list, implying MCC-based blocking is enforced at the transaction level (preventive), distinct from post-hoc flagging (`community-07-mcc-policy-rule.png`).
- A single employee can hold multiple cards of different form factors (Virtual and Physical) simultaneously, each with independently configured monthly limits ($10,000.00 vs $5,100.00 for Olivia Wilson), implying limits are set per-card-instance, not per-cardholder (`community-08-cards-and-limits-table.png`).
- Spend limits can be assigned automatically via a rule/AI toggle ("Automatic limit assignment"), and this can be turned off in favor of a manually "Changed" limit, implying automatic and manual limit-assignment are alternative, mutually distinguishable modes surfaced directly on the mobile card-detail screen (`community-08-cards-and-limits-table.png`).

## Standout details
- The GL-account cell rendered as a literal gray "Select" placeholder inline in a live data table (`-02`) is a good pattern for surfacing an incomplete-required-field state without a separate validation banner — the missing-data state is visible at a glance across many rows simultaneously.
- The "Verified" tooltip's per-field checklist (✓/✗ per field) rather than a single boolean badge (`-04`) communicates exactly which part of automated validation failed — useful microcopy pattern for building trust in automated matching without hiding partial failures.
- Pairing a count-of-total with a running dollar subtotal in the same collapsed-group header string, e.g. "Merchant : Amazon • 2 of 322 ($11,293.98)" (`-01`), lets a user judge materiality of a group before expanding it — avoids needing to open every group to see if it's worth attention.
- The close-progress affordance ("May 2025 close: 15% exported") paired with a horizontal progress bar directly in the Accounting page header (`-02`) turns an abstract backend process (accounting period close) into an ambient, always-visible completion metric.
- Distinguishing "if" condition pills (blue) from "then" action pills (gray) in the MCC rule builder (`-07`) is a small but effective color-coding convention that makes long rule sentences easier to parse at a glance.
- The floating bulk-action toolbar (`-02`) keeps only two lines of text (bold count-and-verb + gray sub-detail) plus one CTA button, resisting the urge to cram many bulk actions into the bar — a restraint worth noting for KEEL's own bulk-action surfaces.
- Card-type (Virtual/Physical) is conveyed by a small icon directly beside the masked card number (`-08`) rather than a separate column, keeping the table dense while still visually scannable.
- On mobile, "Submit reimbursement" is embedded as the first row of the "Latest expenses" feed with a plus-icon instead of being a separate top-level button (`-08` inset) — folds a creation action into a list users already scan.
- "Automatic limit assignment" is paired with an info "i" icon even though it's off (`-08` inset) — signals that explanatory help text should be available for automation toggles regardless of their current on/off state.
