## 1. Design decisions (revised)

### D1. Two layers, explicitly separated (unchanged from v1, tightened by [AMENDED 2])
1. **Decomposition layer (exists):** `paychecks` + components + matches — the reproducible gross→net fact tied to a real deposit.
2. **Ledger booking layer (new, optional per application):** re-post the deposit's live batch so reports show gross income + tax expenses. Booking is **never** via `keel_cmd_set_splits` (its direction guard forbids mixed-sign and must not be weakened — `20260717190000_set_splits.sql:192`). New proc `keel_paycheck_book_splits` writes the mixed-sign batch under the paycheck contract's stricter invariant, using the same correction model (reversal batch + replacement + `journal_revisions`) so undo is a compensating event (Law 2). See [AMENDED 2] for the exact posting set and reimbursement handling.

### D2. 401(k)/HSA/FSA destination account — provenance + connected-account conversion  **[AMENDED 3]**
The v1 "restrict destinations to manual asset accounts" rule is necessary but insufficient: `keel_paycheck_create` (`20260712130000_paychecks.sql:216–235`) **requires** every destination component (retirement_401k, employer_match, hsa, fsa, espp, direct_deposit) to be fully matched to a real posted deposit txn on a single-real-account batch. A template application to a *manual placeholder* account has no such real txn yet. Resolution:

- **Synthetic placeholder deposit + explicit provenance.** When a template line is a `pretax_transfer` (401k/HSA/FSA/ESPP) whose `destination_account_id` is a **manual (unconnected) asset account** (same restriction as `keel_book_transfer_counterparty`), the apply path materializes a **synthetic canonical deposit** into that manual account (its live single-real-account batch is what the paycheck `match` then binds to), and records provenance in a new table **`paycheck_destination_provenance`**: `(household_id, paycheck_id, component_key, destination_account_id, synthetic_txn_id, origin ('synthetic_placeholder'), converted_to_txn_id nullable, converted_at nullable, converted_command_id nullable)`. This makes the "which leg is synthetic" fact explicit and undoable, mirroring `transfer_links.booked_txn` (`20260718130000_transfer_book_counterparty.sql:47`).
- **Connected-account backfill conversion (audited).** New command `paychecks.convert_destination` → `keel_cmd_paycheck_convert_destination`: given a real Plaid-ingested contribution txn that now exists on the (now-connected) retirement account, it (a) validates the real txn's amount/currency/account against the provenance row, (b) posts a compensating reversal of the synthetic placeholder batch (never a DELETE — `journal_revisions`, exactly like `keel_undo_transfer` `:495–522`), (c) re-binds the paycheck match to the real txn via a paycheck edit/supersession (`keel_paycheck_edit` reverse+create, all-or-nothing), and (d) stamps `converted_to_txn_id/at/command_id`. Both legs cannot stay economically active: the placeholder posting is reversed in the same transaction the real match is bound. Idempotent by `economic_event_key = 'paycheck-convert:'||paycheck_id||':'||component_key`; concurrent conversion serialized by `select ... for update` on the provenance row.
- **Locked periods:** if the synthetic placeholder batch's period is locked, conversion refuses with a typed error requiring explicit reopen-with-reason (Law 2); never silently rewrites a locked period.
- Tests: historical Plaid backfill (real contribution arrives weeks later), concurrent conversion (two workers), undo of a converted destination, locked-period refusal (Laws 2,3,9).

### D3. Template model — build on `paycheck_templates`, normalize lines  **[AMENDED 1, 6]**
- **`paycheck_template_lines`** (immutable): `household_id, id, template_id, line_key, kind (paycheck_component_kind), role ('earning','tax','pretax_transfer','posttax_deduction','net_deposit'), amount_kind ('fixed_minor','percent_of_gross_bps','remainder'), amount_minor bigint null, bps int null check (bps is null or (bps > 0 and bps < 10000)), category_ledger_account_id uuid null, destination_account_id uuid null, position int not null`. Constraints: **exactly one** `remainder` line per template (partial unique index on `(household_id, template_id) where amount_kind='remainder'` PLUS a `keel_cmd_paycheck_save_template` check that count=1 — not "at most one"); role↔kind check; `category_ledger_account_id` required for `tax`/`posttax_deduction` when booking; `destination_account_id` required for `pretax_transfer`; composite tenant FKs `(household_id, template_id) → paycheck_templates`, `(household_id, category_ledger_account_id) → ledger_accounts`, `(household_id, destination_account_id) → accounts`. **No implicit SQL defaults on any financial/policy column** (Law 4) — every column NOT NULL or explicitly nullable-by-design; the save command supplies every value.
  - **Aggregate P constraint (`P = Σ bps` across all percent lines) MUST be `< 10000`** — enforced in the save command (not just per-line `bps < 10000`), because per-line bps can each be <10000 yet sum ≥10000, leaving no room for a non-negative remainder. This is the aggregate check v1 lacked. See D4.
- **`paycheck_series_settings`** (mutable pointer + autonomy — the per-series grant Law 2 needs): `household_id, series_id, employer_id, active_template_id, booking_enabled boolean NOT NULL, income_category_ledger_account_id uuid null, autonomy public.autonomy_level NOT NULL, confidence_policy_version text NOT NULL, unique(household_id, series_id)`. **No SQL defaults** — the set-settings command supplies `booking_enabled` and `autonomy` explicitly. `auto_with_log` requires an `active_template_id`. Class-B routing: `off`=never suggest, `suggest`=suggest+approve, `auto_with_log`=explicit grant (see D7 precedence).
- **`paycheck_split_suggestions`** (class-B records, `category_suggestions` pattern + full AI record — **[AMENDED 7]**): `household_id, id, series_id, template_id, template_version, deposit_txn_id, computed_components jsonb, computed_gross_minor bigint, computed_net_minor bigint, source ('detector','agent'), status ('suggested','accepted','dismissed','stale'), applied_paycheck_id uuid null, decided_by, decided_at, ai_response jsonb NOT NULL, confidence numeric NOT NULL, confidence_version text NOT NULL, risk_class public.ai_risk_class NOT NULL check (risk_class='B'), policy_version text NOT NULL`. `ai_response` persists the full BC-v2.1 material-response contract per `AiResponseRecordSchema` (verdict, tldr, confidence, as_of+scope, reason_codes, evidence_refs, proposed_actions, requires_approval, modelVersion, promptVersion, policyVersion). Unique `(household_id, deposit_txn_id, template_id, template_version)` — idempotent re-detection. Stored `computed_components` bind approval to the exact payload (Law 11); acceptance **re-computes server-side and compares** — mismatch ⇒ `stale`.

### D4. Deterministic template application math (Law 1)  **[AMENDED 1]** — EXACT algorithm

One algorithm, TS (`packages/paychecks`, UI preview + property tests) + SQL (server truth), parity-tested. **All arithmetic in bigint; every multiply/divide guarded against BIGINT overflow** (reject if any intermediate exceeds `9223372036854775807`; `keel_paycheck_create` already maps `numeric_value_out_of_range → KEEL_INVALID_COMMAND`, `20260712130000_paychecks.sql:268`).

**Inputs:** net deposit `N` (bigint minor, = observed deposit amount), template lines partitioned into: fixed-minor deductions `F_i`, percent-of-gross lines with basis points `p_i` (each `0 < p_i < 10000`), and exactly one `remainder` line. Earnings are derived (single gross earning line carrying `G`); reimbursements are handled as a distinct additive class (see [AMENDED 2]).

**Constraint (checked at save AND apply):** `P = Σ p_i < 10000`. If `P ≥ 10000`, the template is invalid (`KEEL_INVALID_COMMAND`).

**Step 1 — exact gross selection.** For a paycheck with only fixed deductions `ΣF` and percent deductions summing to `P` bps, net as a function of gross is:
`net(G) = G − ΣF − Σ_i round_half_up(G·p_i, 10000)`  (each percent line independently half-up rounded — this is the accumulation source Codex found).
We must select the **unique** integer `G` such that after per-line rounding the remainder line is a non-negative integer and total deposits reconcile to `N`. Because per-line rounding is non-linear, we do NOT compute `G` by a single closed-form divide. Algorithm:
  1. **Seed** `G0 = ceil((N + ΣF) · 10000 / (10000 − P))` using exact bigint ceil-division (`(a + b − 1) / b` for positive `a,b`). Guard `(N + ΣF) · 10000` against overflow before dividing.
  2. **Local search** `G ∈ {G0 − 2, …, G0 + 2}` (a ±2 window provably contains the solution: per-line half-up rounding perturbs `net(G)` by at most `±(#percent lines)/2` minor units per unit of `G`, and `net` is monotone non-decreasing in `G`). For each candidate compute `taxes_i = round_half_up(G·p_i, 10000)` (bigint: `(G·p_i + 5000) / 10000` with overflow guard on `G·p_i`), `deductions = ΣF + Σ taxes_i`, and `remainder = G − deductions − (Σ other fixed net-deposit lines)`.
  3. **Select** the unique `G` for which `remainder ≥ 0` AND `Σ(all net_deposit lines incl. remainder) = N` AND `Σ earnings = G`. If none exists → emit reason `does_not_reconcile` (no silent fail, no negative remainder). If more than one `G` satisfies (should be impossible given monotonicity — assert and fail closed as an invariant breach), raise `KEEL_INVALID_COMMAND`.
  4. **Remainder role:** the single remainder line is the take-home direct-deposit line; it absorbs exactly the residue `G − ΣF − Σ taxes_i`, guaranteeing `Σ deposits = N` and `reconcilePaycheck` returns ok.

**Worked example (Codex's, now reconciled):** `N = 100000`, one fixed deduction `F = 12300`, three percent lines `p = {1, 1, 246}` bps (`P = 248 < 10000`).
  - Seed `G0 = ceil((100000 + 12300)·10000 / (10000 − 248)) = ceil(1123000000 / 9752) = ceil(115156.68…) = 115157`.
  - At `G = 115157`: `tax_1 = round_half_up(115157·1,10000) = round_half_up(115157,10000) = 12` (`(115157+5000)/10000 = 120157/10000 = 12`); `tax_2 = 12`; `tax_3 = round_half_up(115157·246,10000) = round_half_up(28328622,10000) = (28328622+5000)/10000 = 28333622/10000 = 2833`. `deductions = 12300 + 12 + 12 + 2833 = 15157`. `remainder = 115157 − 15157 = 100000 = N.` ✓ `Σ earnings = G = 115157`, `net = 115157 − 15157 = 100000`, `Σ deposits = 100000`. Reconciles exactly — the naive independent-rounding remainder would have been `100000 − 1 = 99999` (the −1 Codex found) had gross been derived by a single divide of `N` rather than selecting `G` and letting the remainder absorb residue.

**Property tests (TS + SQL parity, Law 1,4,9):** `Σ earnings = G`; `net = N`; `Σ deposits = N`; exactly one remainder line consumed; idempotence; **multi-line rounding** (fast-check over ≥3 percent lines, random bps with `ΣP<10000`, random fixed lines, random `N` up to `10^12`) asserting the selected `G` reconciles and remainder ≥ 0; **boundary** (`P` just under 10000, `N=0`, single-cent residues, max-bigint `N`); **TS↔SQL parity** (identical `G`, taxes, remainder for a shared fixture corpus). Fixtures fictional (no real employer strings — CLAUDE.md ops fact).

### D5. Booking posting set + reimbursement/employer-match balance  **[AMENDED 2]**
`keel_paycheck_book_splits` computes and posts the mixed-sign batch and **computes Σ=0 per currency itself** (not relying only on the deferred trigger, which stays as backstop — Law 3). It **REUSES `keel_insert_postings`** (`20260710210600_command_procs.sql:141`) for the actual insert (tenant + currency validation + entity derivation already there — not reimplemented) and validates all target currencies against each ledger account.

Enumerate EVERY supported component kind and its posting:
| Component kind | Posting into booking batch |
|---|---|
| `gross_salary`/`bonus`/`commission` (earnings, Σ=G) | income category `−G` |
| `direct_deposit` (net) | cash/checking `+net` |
| `federal_/state_/local_/fica_withholding`, `benefit`, `garnishment`, `rsu_withholding` | expense category `+amount` |
| `retirement_401k`, `hsa`, `fsa`, `espp` (pretax transfer) | destination asset ledger account `+amount` (NOT expense) |
| `reimbursement` (addition) | **`−R` offset to a reimbursement receivable/clearing ledger account** — this is the fix: without it the batch sums to `−R ≠ 0` |
| `employer_match` (employer-side addition, not withheld from net) | **paired legs: employer-match income/contra `−M` and destination asset `+M`** (nets to 0 within the batch; the match is not part of net take-home) |

**Balance identity:** with reimbursement offset and employer-match paired, `Σ = (+net) + (−gross) + (Σ deductions) + (−R reimbursement offset) + (employer-match 0) = net − gross + Σdeductions − R`. Since `net = gross + R − Σdeductions` (from `reconcilePaycheck` `packages/paychecks/src/index.ts:85`), substituting gives `Σ = 0` exactly. **If a template/paycheck carries a reimbursement or employer-match kind but the series has no configured reimbursement-clearing / employer-match ledger account, `keel_paycheck_book_splits` REJECTS before booking** (typed `KEEL_INVALID_COMMAND`) rather than posting an unbalanced batch. The proc re-asserts `Σ=0 per currency` on its computed postings before calling `keel_insert_postings`; the deferred balance trigger is the backstop (Law 3).

### D6. Auto-apply hook location (unchanged shape; identity hardened by [AMENDED 5])
In `processRecurringDetection` (worker), after reap: `keel_detect_paycheck_split_suggestions(household)` emits suggestions for confirmed series with an active template + autonomy≠off, for matched-occurrence deposits with no active paycheck + no live suggestion. Then for `autonomy='auto_with_log'`, `keel_auto_apply_paycheck_splits(household)` applies via the internal apply core (stable `economic_event_key='paycheck-tpl:'||series||':'||deposit`), audited, non-fatal on error, idempotent by unique key + `keel_idempotency_check`. Both procs owned by the internal principal (see [AMENDED 5]); execute service_role only.

### D7. Autonomy precedence + confidence routing  **[AMENDED 4]**
- **Precedence:** the **per-series `paycheck_series_settings.autonomy` is authoritative for a specific series**; the household-level `approval_policies` class-B row (`20260710210100_identity_authz.sql:98`, seeded 'suggest' `seed.sql:155`) is the **ceiling/default**. Effective autonomy for a series = `min(household_class_B_autonomy, series_autonomy)` under the ordering `off < suggest < auto_with_log`. A series can never exceed the household class-B ceiling; if household class-B is 'off', no series suggests or auto-applies regardless of its own setting. This precedence is documented in NOTES.md and enforced in `keel_detect_paycheck_split_suggestions` / `keel_auto_apply_paycheck_splits`.
- **Within-class routing (server-side thresholds):** a `confidence_version`-stamped threshold table maps calibrated `confidence` → routing outcome whose **only** possible values are `off` / `suggest` / `auto_with_log` — all within class B (Law 10: confidence routes within a class, never across). Below the suggest threshold ⇒ no suggestion; between suggest and auto thresholds ⇒ suggest+approve; at/above auto threshold **AND** series granted `auto_with_log` ⇒ auto-with-log. Persisted per suggestion: `confidence`, `confidence_version`, `risk_class='B'`, `policy_version`.
- **Audit coverage:** every suggestion transition (`suggested→accepted|dismissed|stale`), paycheck creation, booking revision IDs, the policy/grant version in effect, and the undo linkage all land in `audit_log` via `keel_finish_command` (`20260710210600_command_procs.sql:129`).

### D8. Undo (Law 2) (unchanged, extended for converted destinations)
`paychecks.unapply` → `keel_cmd_paycheck_unapply`: reverse the paycheck (`keel_paycheck_transition_core('reversed')`), reverse the booking batch if present (compensating revision), reverse any synthetic placeholder destination batches not yet converted, mark originating suggestion `dismissed`. Plain `paychecks.reverse` on a template-applied paycheck is blocked with a typed error pointing to `unapply`. Converted destinations (real Plaid txn bound) are NOT reversed by unapply — they are real facts; unapply unbinds the paycheck match only.

### D9. Trusted server-side identity boundary for agent backfill  **[AMENDED 5]**
The v1 `actor.kind='agent'` down-shift is deleted (forgeable — `api/index.ts:2464` passes client actor; procs use JWT). Replace with a **trusted principal boundary**:
- **Suggestion-only agent path.** A named internal principal (`keel_agent`, non-login, non-super, non-BYPASSRLS, minted in migration) owns `keel_agent_suggest_paycheck_split(household, series, deposit, ai_response)` which can ONLY insert a `paycheck_split_suggestions` row with `source='agent'`, `status='suggested'`. Execute granted to `service_role` (the worker/agent runtime) ONLY; `authenticated`/`anon` revoked. The apply and decision procedures are **REVOKED from `keel_agent`/`service_role`** — an agent can suggest, never apply or approve.
- **Human apply derives identity from JWT + validates an approval token.** `keel_cmd_paycheck_apply_template` (and `keel_cmd_decide_paycheck_split_suggestion`) run as `keel_api`, derive actor from `keel_actor_from_jwt()`, and require a **redeemed approval token** bound to the exact payload (see [AMENDED 7] / HARD GATE). There is no code path by which a caller-supplied `actor` JSON can escalate.
- **Direct-RPC bypass test (Laws 2,7,10,11):** a test connecting as `service_role`/`keel_agent` and calling `keel_cmd_paycheck_apply_template` / `keel_cmd_decide_paycheck_split_suggestion` directly MUST be denied (grant/revoke), and calling `keel_agent_suggest_paycheck_split` with a forged `actor.kind='user'` MUST NOT change the recorded actor (it is derived, not trusted).

### D10. Reuse typed AI + approval-token schemas + HARD GATE  **[AMENDED 7], GATE]**
- **Reuse existing schemas (Law 11).** Suggestions persist the full `AiResponseRecordSchema` in `ai_response` (`packages/contracts/src/ai.ts:23`); approvals bind `ApprovalTokenSchema` (`:44`). v1's reduced `reason_code`/`evidence`/`computed_components`-only record is superseded.
- **Apply-on-the-live-primitive with the HARD GATE.** `keel_cmd_paycheck_apply_template` binds **ONE local `v_payload`** (the server-normalized apply payload: series, template_id, template_version, deposit_txn_id, computed components) and passes that SAME `v_payload` variable to BOTH:
  1. `keel_approval_token_redeem(p_household_id, p_token_id, p_command_id, p_actor, 'paychecks.apply_template', v_payload, p_proposal_version)` — which re-hashes `v_payload` and compares to the bound `payload_sha256` (`20260720100000_approval_tokens.sql:292`), AND
  2. the paycheck materialize/book call (build the `keel_paycheck_create`-shape input from the SAME `v_payload`, then `keel_paycheck_book_splits`),
  in **one transaction**. Because redeem does not return the payload (advisory A), the guarantee "exact bytes approved = exact bytes executed" holds only by this single-variable binding. **pgTAP frozen first** proving a redeem-payload-A / execute-payload-B attempt is impossible by construction (there is no second payload variable in scope). Issue side: `paychecks.issue_apply_token` → `keel_approval_token_issue(..., p_command='paychecks.apply_template', p_normalized_payload=v_payload, p_proposal_kind='paycheck_split', p_proposal_ref=suggestion_id, p_proposal_version=template_version, p_policy_version=..., p_ttl_seconds=...)`.
