# Review queues & approval workflows

## Convergent patterns
(Behaviours ≥3 competitors share that KEEL does not do. Strongest signals — the founder explicitly wants these.)

1. **Review is surfaced *at the transaction*, not only on a dedicated page.** Copilot marks each unreviewed txn with a "• To Review" status right in its detail header and shows a live count badge on the "Transactions" nav item (`copilot/community-01`, `copilot-community-01.md`; badge "16"/"18"/"5" varies with the unreviewed count, `copilot-community-02.md`). Ramp puts an AI verdict box directly on the transaction (`ramp/community-04`). YNAB flags rows in the register ("approving and matching," FEATURE-GAP sources). Brex flags the expense card itself (`brex/community-10`). KEEL's Review is a single siloed page one click away, with **no badge, no count, and no review affordance in the Ledger or Recurring pages where the items actually live** (`review-desktop.png`, `keel-core-01.md` §IA: "Review … positioned between Statements and Connections … despite its content being entirely about AI suggestions for recurring/transfers/categorization, which live under different top-level nav items").

2. **A dashboard triage card + bulk "mark all reviewed."** Copilot's Dashboard has a "Transactions To Review" card capped at ~5 rows with a full-width "✓ Mark all as reviewed" button and a "VIEW ALL ↗" escape hatch (`copilot/community-10`, `copilot-community-02.md`); the iPhone Dashboard repeats it ("So far today" → full-width "MARK AS REVIEWED", `copilot-iphone-01.md`). Ramp bulk-approves and discloses it as an aggregate ("971 transactions were automatically approved by agent", `ramp/community-04`). Brex has a floating bulk-action toolbar (`brex/community-02`). Monarch has "✓ Edit multiple" (`monarch-community-02.md`). KEEL's Home dashboard has **no review card at all** (`keel-core-01.md` §Home), and the Review page has **zero interactive controls** (`keel-core-01.md` Controls: "Review: no interactive controls are visible").

3. **Every AI suggestion states its reason and evidence inline — a "because" plus per-field validation — not a bare verdict.** Ramp: "Transaction complete / Ramp found no issues and suggested it be approved" with bulleted rationale ("The expense is related to an active business trip", "Receipt has been auto-verified") and thumbs up/down feedback (`ramp/community-04`); the receipt popover lists three checks "Verified amount / date / merchant" with a "Report incorrect receipt verification" contest link (`ramp/community-06`). Brex: "flagged by Brex AI because: • High risk item detected on receipt: Alcohol" and a per-field "Verified" checklist showing Date ✓ / **Amount ✗** / Merchant ✓ (`brex/community-04`, `brex/community-10`). Copilot shows the *previous* category crossed-out above the picker so you see exactly what you're replacing (`copilot/community-02`). KEEL's Law 11 *mandates* this (verdict, tldr, confidence, reason_codes, evidence_refs, before→after payload) yet **no populated review card exists to carry it** (`keel-mobile-04.md` Open questions: "What does a populated Review card look like (approve/dismiss controls, confidence display, reason codes, evidence refs per Law 11) — not evidenced").

4. **The audit/activity trail is a human-readable, per-record, drill-through feed — with the changed value shown.** Ramp's "Activity" timeline: actor avatar + name + timestamp + plain-English cause ("Approved transaction because it's in policy and no other issues were found"; "Updated the memo" + a chip showing the new value "Office snacks and beverages") (`ramp/community-09`, `ramp-community-02.md`). Brex notifications: "Brex Assistant added receipt and memo to $56.00 at Delta" with a "View" deep-link and read/unread dots (`brex/community-11`). Monarch pairs deltas beside every figure. KEEL's audit surface (Settings → Recent activity) leaks raw internal event names and floods with un-grouped duplicates (see REVIEWAPPROVAL-2).

## Findings

### REVIEWAPPROVAL-1 — Review is a dead-end silo, disconnected from the Ledger/Recurring/Home surfaces where suggestions live and where users work [P1]
- **Evidence:** `review-desktop.png`, `review-mobile-390.png`, `keel-core-01.md` (§IA ¶17; Controls: "Review: no interactive controls"), `keel-mobile-04.md`; contrast `copilot/community-01`, `copilot/community-10`, `copilot-community-02.md`.
- **Competitors:** Copilot never makes you go to a "review page" — the review status rides on the transaction ("• To Review" in the detail header, `copilot/community-01`), a numeric badge on the Transactions nav item counts the backlog, AND a Dashboard "Transactions To Review" card lets you clear it from Home with "Mark all as reviewed" (`copilot/community-10`). Three independent entry points into the same queue; the register itself is the queue. Ramp/Brex fold review into the record and into notifications.
- **KEEL today:** Review is one top-level page between Statements and Connections, rendering a single dashed empty box ("Nothing to review"). It is the *only* place suggestions appear — nothing on Home, no badge on the nav item, no "N need review" cue in the Ledger toolbar, no review state on Ledger rows. A user has to remember to visit a page that is empty 90% of the time. The three suggestion types it aggregates (recurring, transfer matches, categorizations) each belong to a different nav destination (Recurring, Ledger), so the queue is decoupled from context (`keel-core-01.md` ¶17).
- **Fix:** (a) Add a live count badge to the Review nav item and a compact "To review (N)" card on Home mirroring Copilot's dashboard card, capped at ~5 items with "Review all →". (b) Add a per-suggestion inline approve affordance in-context: transfer-match banner on the two Ledger rows, "confirm" on Recurring suggested rows, so the Review page becomes an *aggregator* not the *only* surface. (c) When empty, the badge disappears rather than showing "0".
- **Maps to:** W1.5 (Review badge — planned, not built; extend to Home card + in-context affordances).

### REVIEWAPPROVAL-2 — The audit trail (the trust surface) leaks raw internal event names and floods with un-grouped duplicate rows, with no detail, filter, or drill-through [P1]
- **Evidence:** `settings-desktop.png` (Recent activity card — ~18 consecutive identical "ingest.apply_action · KEEL (automatic)" rows, all `2026-07-14 02:14`), `keel-ops-03.md` (§Layout ¶6, §Standout, Open questions ¶6: "Notable copy inconsistency: some audit rows use humanized narration … while others surface a raw internal event name verbatim ('ingest.apply_action') — a developer-facing string leaking into user-facing UI").
- **Competitors:** Ramp's Activity feed is plain-English and causal, one line per event with actor avatar + relative timestamp, and shows the *value that changed* as a chip ("Updated the memo" → "Office snacks and beverages") (`ramp/community-09`, `ramp-community-02.md`). Brex notifications deep-link each entry to its record via a "View" button and encode read/unread (`brex/community-11`). Neither ever shows an internal event slug; neither repeats the same event 18× with no rollup.
- **KEEL today:** Half the rows are humanized ("Auto-categorized new transactions", "Decided a transfer match · You"), the other half are the raw proc name `ingest.apply_action`. Even the humanized rows give no detail: no count ("categorized how many?"), no before→after, no link to the affected transaction, no filter/search/pagination — the list just runs off the bottom of the card. This is the primary user-facing realization of Law 2/9 ("everything is recorded in an append-only audit trail") and it currently reads like a debug log.
- **Fix:** (a) Map every internal event key to a human sentence (`ingest.apply_action` → "Imported N transactions from Chase"); never render a proc name. (b) Collapse runs of identical same-minute events into one row with a count ("Imported 47 transactions"). (c) Give each row a before→after summary and a click-through to the record (Law 9 "source rows on every material result"). (d) Add actor icon, filter (You / KEEL), and pagination. Copy the Ramp/Brex feed grammar.
- **Maps to:** W1.10 (Settings Activity card — extend: the current build is the naïve version this finding replaces).

### REVIEWAPPROVAL-3 — No populated review card exists, so Law 11's typed-response contract (verdict · confidence · reason_codes · evidence_refs · exact payload) has no UI [P1]
- **Evidence:** `review-desktop.png` / `review-mobile-390.png` (empty state only), `keel-mobile-04.md` (Open questions ¶1), CLAUDE.md Law 11; contrast `ramp/community-04`, `brex/community-04`, `copilot/community-02`, `copilot/community-03`.
- **Competitors:** Ramp's verdict box pairs a headline verdict ("Transaction complete"), a one-line summary ("Ramp found no issues and suggested it be approved"), an expandable bulleted rationale, an evidence link ("auto-verified"), AND a thumbs up/down calibration control — all above the approve/reject bar (`ramp/community-04`, `ramp/community-03`). Brex renders a per-field validation checklist with explicit pass/fail glyphs (Date ✓ / Amount ✗ / Merchant ✓, `brex/community-04`). Copilot shows the exact value being replaced (old category struck through above the picker, `copilot/community-02`). In every case the reviewer sees *what will change and why* before committing.
- **KEEL today:** The card is unbuilt; the empty state only promises "each waiting for your approval." There is no evidenced design for how a suggested category / transfer match / recurring series presents its confidence, its reason codes, its evidence (the source rows), or the exact before→after it will write. Approving a suggestion you can't inspect violates the spirit of Law 11's "approval tokens binding exact payload" and the "TLDR first, proof on demand" principle.
- **Fix:** Design the review card as the literal typed-AI-response record: (1) verdict + tldr line; (2) confidence as a calibrated chip; (3) the exact before→after (e.g. "Food & Drink → Groceries", or transfer legs shown side-by-side with an amount-equality check à la Ramp's "Selected bill matches expense amount", `ramp/community-05`); (4) collapsible reason_codes + evidence_refs (the matched source rows, the rule that fired); (5) Approve / Dismiss / Edit; (6) an as-of/scope footnote (KEEL already does this well on Reports — reuse the pattern from `keel-money-02.md` §Standout).
- **Maps to:** NEW (depends on gaps #2/#10 categorization + typed-AI node; this is the review-surface half).

### REVIEWAPPROVAL-4 — No bulk actions in the review queue; the Ledger's "Select" mode is unbuilt/unshown [P1]
- **Evidence:** `keel-core-01.md` (Controls: "☑ Select … presumably surfaces a bulk-action bar … not captured"; Open questions ¶2), `keel-mobile-04.md` (Open questions ¶2), `review-desktop.png` (no controls); contrast `copilot/community-01` (bulk bar), `copilot/community-10` ("Mark all as reviewed"), `brex/community-02` (floating bulk toolbar), `ramp-community-01.md` ("Sync (2)" batch), `monarch-community-02.md` ("Edit multiple").
- **Competitors:** Copilot's selection bar reads "2 selected [ Category ] [ ✓ Review ] [ Type ] ⋮" — set-category, mark-reviewed, and set-type in one gesture over N rows (`copilot/community-01`). Its Dashboard card and iPhone both offer full-width "Mark all as reviewed." Brex keeps the floating bar deliberately minimal (count + one primary CTA). Ramp bulk-marks rows "Ready" and batch-syncs. Bulk clearing is the single biggest friction-reducer for a review backlog.
- **KEEL today:** The Review page has no select-all, no "approve all high-confidence," no bulk-dismiss. The Ledger has a "Select" button but its post-tap bulk bar is not evidenced anywhere and W1.3 (bulk categorize) is planned, not shipped. So there is currently no way to clear a backlog except one item at a time.
- **Fix:** (a) On the Review page, add select-all + a floating bar with "Approve N", "Dismiss N" (Brex-style: count + primary CTA, resist cramming). (b) Offer "Approve all high-confidence" as a single action, gated to the auto+undo band (Law 10). (c) Ship the Ledger bulk-category bar (W1.3) with a "✓ Reviewed" action alongside category.
- **Maps to:** W1.3 (Bulk categorize — extend to bulk approve/dismiss on Review + a review flag).

### REVIEWAPPROVAL-5 — Transactions carry no "needs review" state, so the ledger can't show what's outstanding [P1]
- **Evidence:** `keel-core-01.md` (Ledger rows show a "PENDING" badge = bank pending/posted, `keel-core-01.md` §Business rules ¶3; there is no review-status field), `ledger-desktop.png`; contrast `copilot/community-01` ("• To Review" per txn + reviewed = checkmark), `copilot-ipad-01.md` ("To review" status distinct from confirmed; nav badge "11"), YNAB approve/match (FEATURE-GAP sources).
- **Competitors:** Copilot models review as a first-class per-transaction flag: unreviewed rows say "To Review," and once reviewed the state clears (and the nav count drops). This lets the register itself be filtered to "unreviewed," and lets the count badge be authoritative. Ramp/Brex model an analogous "Mark Ready"/submitted state per row.
- **KEEL today:** The only per-row status is "PENDING" (a bank pending/posted signal on the two newest rows), which is orthogonal to whether *you or the AI still need to look at it*. There is no "reviewed/unreviewed" attribute, no filter for it, and therefore no trustworthy backlog count. Auto-categorization happens ("Auto-categorized new transactions" in the audit log) but the user has no way to see *which* auto-categorized rows they haven't verified.
- **Fix:** Add a review-status field (unreviewed / reviewed) settable per row and in bulk; surface it as a subtle marker on Ledger rows (a dot, not red — reserve red for money) and as a Ledger filter chip ("Needs review (N)"); mark a row reviewed automatically when the user edits its category or approves its suggestion. Feed the same count into the nav badge (REVIEWAPPROVAL-1).
- **Maps to:** NEW (small backend field + FE; complements W1.2 filters, W1.5 badge).

### REVIEWAPPROVAL-6 — No confidence routing and no aggregate "here's what we auto-did" disclosure; everything is flat suggest→approve [P2]
- **Evidence:** CLAUDE.md Law 10 (Class A auto+undo: merchant normalization, dedupe, narration; "confidence routes within a class"), `keel-ops-03.md` (audit shows "Auto-categorized new transactions · KEEL (automatic)" — auto-apply already happens); contrast `ramp/community-04` (aggregate auto-approval banner), `copilot-ipad-01.md` (AI-suggested category with a sparkle, confirmed via "✓ Review").
- **Competitors:** Ramp auto-approves in-policy transactions and discloses it as a *dismissible, collapsible aggregate* ("971 transactions were automatically approved by agent · 3d ago · Purchases totaling $84,466.99 were in policy · Collapse", `ramp/community-04`) rather than flooding the queue with 971 individual approvals — progressive disclosure of the auto-tier. Copilot auto-applies a category (sparkle mark) and lets you confirm-in-bulk, so only genuinely-uncertain items demand attention.
- **KEEL today:** KEEL already auto-categorizes on sync ("Your own edits always win," Rules card, `settings-desktop.png`) but the review model in the UI is uniformly "suggest → approve," with no visible tier for "we did this automatically, undo if wrong," and no batched summary of what was auto-done. The risk: either the queue fills with low-value confirmations, or auto-applied changes happen with no digestible disclosure — both erode the Law 10 ladder's legibility.
- **Fix:** (a) Route by confidence *within* a class: high-confidence categorizations auto-apply with an undo-able badge; only mid/low confidence enter the Review queue (surface top-2 candidates, Copilot pattern). (b) Add a collapsible "KEEL auto-categorized N transactions since your last visit — review or undo" banner at the top of Review/Ledger, mirroring Ramp's aggregate. (c) Keep Class C (forecasts) and Class D (money movement) out of any auto path.
- **Maps to:** NEW (relates to FEATURE-GAP #10 AI categorization node + gap #22 autonomy policies).

### REVIEWAPPROVAL-7 — No feedback / correction loop on AI suggestions (thumbs, "report incorrect") [P2]
- **Evidence:** contrast `ramp/community-04` (thumbs up/down on the verdict box), `ramp/community-06` ("Report incorrect receipt verification"); KEEL: no such control anywhere (`review-*` empty, `keel-*` census).
- **Competitors:** Ramp attaches a thumbs up/down directly to each AI verdict and a "report incorrect" link to each auto-verification — a lightweight calibration signal that also builds trust ("the system can be told it's wrong"). This is how a suggest→approve product earns the right to escalate autonomy.
- **KEEL today:** When the review card ships, dismissing a suggestion is the only signal, and it's ambiguous (dismiss = "wrong" or "not now"?). There's no explicit "this suggestion was wrong" channel to feed calibration (Law 11 requires *calibrated* confidence — that needs a feedback source).
- **Fix:** On each review card and each auto-applied badge, add a "wrong?" / thumbs-down affordance that (a) reverts the change and (b) logs a labeled correction event for calibration. Distinguish "dismiss (not now)" from "reject (wrong)" as separate outcomes in the audit trail.
- **Maps to:** NEW (feeds gap #10 typed-AI confidence calibration).

### REVIEWAPPROVAL-8 — No multi-approver / approval-chain surface for entity & household mode, despite the schema for it [P2]
- **Evidence:** FEATURE-GAP #22 (approval_policies with risk_class A–D, autonomy off/suggest/auto_with_log — "framework present … No AI actually routes through it"), `keel-ops-03.md` (Household card: "Your role → Owner"), CLAUDE.md Laws 7/9; contrast `ramp/community-03` (ordered approvers "Approvals 0 of 2", reorderable/removable), `brex/community-03` (threshold approvals "Payment ≥ $50K → any other admin"), `brex/community-09` ("For approval" bill-pay tab).
- **Competitors:** Ramp's approval detail shows an ordered, numbered approver chain with an "X of Y" progress counter, per-approver remove/reorder, and per-approver "Request changes / Request repay" (`ramp/community-03`). Brex offers threshold-based routing as a first-class settings card with a "Default" posture (`brex/community-03`) and a "For approval (4)" queue tab (`brex/community-09`). This is exactly the multi-entity/LLC workflow KEEL is positioned for.
- **KEEL today:** KEEL has households, memberships, roles (Owner), and an approval_policies table with risk classes — but zero UI: no approver assignment, no "awaiting approval from X," no threshold rules, no "X of Y" progress, no queue segmented by "who needs to act." For a system whose thesis is personal *+ entity* finance, this is unclaimed whitespace and a live gap.
- **KEEL today (status-adjacency note):** Ramp places the approval status ("Awaiting review from Meredith Palmer") *directly under the money figure* ("$130.00 at Google Domains") — the exact "status adjacent to the number it qualifies" law KEEL states (Law 8). Adopt that placement.
- **Fix:** For entity households, add an approval-chain object on high-risk actions (owner draws, large transfers, statement close): ordered approvers, "Awaiting X · N of M", threshold rules in Settings (Brex card pattern), and a "For approval" filter in the Review queue. Keep Class D (money movement) disabled per Law 10 — this is approval *of records/coding*, not payment execution.
- **Maps to:** NEW (activates FEATURE-GAP #22 autonomy-policy framework in the UI).

### REVIEWAPPROVAL-9 — Review queue is undifferentiated: no per-type segmentation, grouping, or type-scoped bulk actions [P2]
- **Evidence:** `keel-mobile-04.md` (§Business rules: "Review queue is explicitly scoped to three suggestion types … Recurring series, transfer matches and categorizations"), `review-desktop.png` (single flat container); contrast `brex/community-02` (Prepare/Review/Exported tabs with counts), `brex/community-09` (Drafts/For approval/For payment), `ramp-community-02.md` (Bill Pay status tabs), `copilot/community-10` ("So far today" date grouping).
- **Competitors:** Brex and Ramp both model the review backlog as status/stage tabs each carrying a live count ("Prepare 1,000 / Review 200 / Exported 150", `brex/community-02`), so a reviewer can attack one kind of work at a time and see how much of each remains. Copilot groups the review card by time.
- **KEEL today:** The empty-state copy lumps three structurally different suggestion types into one undifferentiated queue with no tabs, no per-type counts, and (implied) no way to "approve all transfer matches" separately from "approve all categorizations." Transfer-match approval (a correctness action — prevents double-counting) and a low-stakes category suggestion have very different risk profiles but would sit in one flat list.
- **Fix:** Segment the Review queue by suggestion type with per-type counts ("Transfer matches 3 · Recurring 2 · Categories 11"), each independently bulk-actionable. Order by risk (transfer matches first — they affect cash-flow/net-worth correctness). Reuse KEEL's existing calm section-header pattern rather than neon tabs.
- **Maps to:** NEW (structures the Review page; complements REVIEWAPPROVAL-3/4).

### REVIEWAPPROVAL-10 — No keyboard-driven review and no mobile swipe loop for clearing the queue fast [P3]
- **Evidence:** `review-desktop.png` / `review-mobile-390.png` (no per-item controls, no keyboard hints); contrast `ramp/community-03` ("Next [J]" and "Approve [⌘][↵]" key badges rendered inside the buttons), `copilot-iphone-01.md` (card-first review, full-width "MARK AS REVIEWED"; the "swipe/approve" loop the brief names).
- **Competitors:** Ramp teaches power-user shortcuts in-place: "Next [J]" advances the queue, "Approve ⌘↵" commits, so a reviewer can clear dozens without touching the mouse (`ramp/community-03`, `ramp-community-01.md` §Standout). Copilot's phone review is a stack of large cards cleared with a tap/swipe. For a desktop-first tool with a phone-capable mandate, both idioms matter.
- **KEEL today:** No keyboard model for the queue (approve/dismiss/next), and the mobile Review is just the empty box — no card-stack, no swipe-to-approve / swipe-to-dismiss gesture. Clearing a backlog on a phone would be tap-heavy.
- **Fix:** (a) Desktop: J/K to move through the queue, Enter/⌘↵ to approve, Esc/X to dismiss, with the key hints shown on the buttons (Ramp pattern). (b) Mobile: a swipeable review card stack — swipe right = approve, left = dismiss, tap = expand proof — the phone form of the desktop queue.
- **Maps to:** NEW (interaction polish on the review card from REVIEWAPPROVAL-3).

### REVIEWAPPROVAL-11 — Empty state doesn't distinguish "detection hasn't run" from "ran, found nothing," and offers no "last checked" / manual re-check [P3]
- **Evidence:** `review-desktop.png` copy ("Nothing to review / Recurring series, transfer matches and categorizations will surface here as suggestions"), `keel-mobile-04.md` §States; contrast the Recurring page which *does* disclose cadence ("Detection runs nightly", `keel-money-02.md` §States) — an inconsistency between two KEEL surfaces that describe the same detection jobs.
- **Competitors:** Copilot's support hub sets response-time expectations inline; Ramp's OCR banner sets a time expectation and offers "come back later" (`ramp/community-11`). The bar is: tell the user *why* it's empty and when it'll change.
- **KEEL today:** The Review empty state is calm and well-written but ambiguous — it can't tell the user whether the queue is empty because detection is up-to-date or because it hasn't run against recent syncs. No "last checked 21m ago" stamp (KEEL already shows exactly this on the Accounts sync — `keel-core-01.md` "Updated 21m ago"), no manual "Check for suggestions now."
- **Fix:** Add a "Last checked · <time> · detection runs nightly" line to the Review empty state (reuse the Accounts freshness stamp), and — since sync is user-triggerable — a "Check now" affordance. Keep the reassuring tone.
- **Maps to:** NEW (copy + a timestamp read; trivial).
